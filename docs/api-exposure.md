# Kubernetes / Talos API の公開方針

Issue #16。2026-09-27時点の既存実装を方針として明文化する。
この変更ではパケットフィルタを変更せず、ノード間・管理経路を維持する。

| 経路 | 現状と目的 | 保護 |
|---|---|---|
| Internet → CP外部IP:6443 | 送信元制限なし。直接管理とAPI接続 | TLS、クライアント認証、RBAC |
| ノード → Kubernetes API | KubePrism経由のAPI接続。閉域だけと仮定して外部側を遮断しない | クラスタ認証・TLS |
| 運用者 → Omni:8100 | prodの日常的なkubectl経路 | Omni認証・クラスタ権限 |
| 踏み台 → ノード:50000 | Talos管理・緊急復旧 | パケットフィルタで送信元制限。通常モードはTalos認証も使用 |
| クラスタ外部CIDR → ノード:50001 | trustd証明書配布 | 外部CIDR制限 |

実装の正本は `terraform/packet-filter.tf`。受信のみ・ステートレスのため、
戻り通信用の32768–61000許可がある。50000/50001はこの範囲に含まれるので、
個別allow → 個別deny → 戻り通信allow の順序を変えない。
80/443の許可もノードのeth0全体に適用され、VIPの宛先だけを選択していない。
高位ポートのallowはセッション追跡ではないため、その範囲に管理サービスを追加する場合は
個別deny/allowの設計が必要。NodePortもこの範囲と重なる可能性がある。

## 認証・運用の前提

- Talosのmaintenance APIは未認証なので、50000は一般公開しない。
- Kubernetes APIのネットワーク到達性と認可を区別する。未認証のAPI操作は拒否する。
- devのOIDC設定をそのままprodへ適用しない。prodの日常操作はOmni経由。
- 公開6443の縮小は将来の別変更とし、KubePrism・Omni・緊急経路の実トラフィックを
  確認してから段階的に行う。今回の資料不一致だけを理由に踏み台限定へ戻さない。

## 検証記録

2026-09-27、各クラスタの `kube-root-ca.crt` で証明書を検証した上で、
クライアント証明書・Bearer tokenなしで `https://<CP1外部IP>:6443/api` を取得した。

| 対象 | 結果 |
|---|---|
| dev CP1 (27.133.146.100) | HTTP 401 |
| prod CP1 (163.43.86.196) | HTTP 401 |

TLS検証を無効化する `-k` は使用していない。CP2/CP3の個別到達性や
認証済み各主体のRBAC網羅検査はこの確認に含まない。
prodの予約API VIP (163.43.86.199) はこの確認元から接続タイムアウトだった。
Omni管理のprodではこの予約値を稼働中VIPとみなさず、Omni API proxyを使用する。
